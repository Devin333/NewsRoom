## Context

`PaperRagApplicationService.rag_ask(generate=True)` runs the bounded Paper RAG session and returns a `transcript_id`, while `framework.harness.rag.replay` can replay a transcript dictionary. The missing link is durable storage for the transcript generated by the service request, plus a local command that can load the stored transcript and run replay by id or file path.

## Goals / Non-Goals

**Goals:**
- Persist gated Paper RAG ask transcripts after the session finishes.
- Keep transcript storage at the interface/service boundary so Harness stays storage-agnostic.
- Provide a deterministic local replay command that reads persisted JSON and calls `replay_rag_session`.
- Make the persisted artifact discoverable from the gated response payload.

**Non-Goals:**
- Changing bounded RAG replay semantics.
- Persisting retrieve-only RAG requests.
- Adding database-backed transcript storage.
- Persisting full context snapshots or external artifacts beyond the transcript JSON.
- Exposing a new public HTTP API in this change.

## Decisions

1. Store transcripts with an interface-layer file store.
   - Rationale: `.newsroom/rag/transcripts` is application/runtime storage, not a framework concern.
   - Alternative: write directly inside `BoundedRAGSessionController`. Rejected because framework code should not know NewsRoom local paths.

2. Use deterministic hashed filenames derived from `transcript_id`.
   - Rationale: transcript ids can contain URI characters and slashes. A hash preserves lookup-by-id without unsafe filenames.
   - Alternative: percent-encode ids into filenames. Rejected because very long ids can produce unwieldy paths.

3. Persist an envelope around `transcript.to_dict()`.
   - Rationale: the envelope allows schema versioning and stable metadata while replay consumes the nested transcript payload.
   - Alternative: write raw transcript dictionaries. Rejected because it leaves no place for storage metadata or future migrations.

4. Add `scripts.dev replay-rag` as the local operator entry point.
   - Rationale: this follows existing `scripts.dev` no-network operational checks and keeps replay easy to run from Windows PowerShell.
   - Alternative: create an `interfaces.cli.news` command. Deferred because this change only needs a local audit utility.

## Risks / Trade-offs

- [Risk] Transcript payloads can contain question text and generated answer text. -> Mitigation: keep files under local `.newsroom/` runtime storage and do not include them in response bodies.
- [Risk] Persisting every gated ask creates local file growth. -> Mitigation: store one compact JSON envelope per gated request; retention policy can be added later.
- [Risk] Replay by id depends on the same hashing scheme used at write time. -> Mitigation: centralize filename mapping in the transcript store and test load-by-id.
